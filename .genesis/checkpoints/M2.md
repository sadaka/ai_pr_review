## Quiz-me Q+A · 2026-09-04
1. **Design decision** — Why does `mark_seen` happen before `enqueue_review`, and what does `unclaim` exist to handle?
   - User's first answer: to respond to the GitHub webhook before it times out. Corrected: order doesn't change response latency (both steps happen before responding either way). The real reason is idempotency-on-retry — claiming the dedup key first prevents a crash/failure between "enqueue" and "mark-seen" from letting a GitHub redelivery double-enqueue the job. The cost is the flip case (enqueue fails after the claim succeeds), which is what `unclaim` rolls back so a legitimate redelivery isn't permanently swallowed. User confirmed understanding after the correction.
2. **Edge case** — Redis completely down: what does GitHub see, is anything silently dropped?
   - Explained (user requested the explanation rather than answering cold, then confirmed understanding): `mark_seen` exhausts its retries, raises, the handler's broad `except Exception` returns 503 before any claim is made — nothing to roll back. GitHub auto-redelivers on non-2xx, so nothing is lost. After 3 consecutive failures the circuit breaker trips open (fails fast, 30s cooldown before the next probe) instead of every request paying the full retry delay during an outage.
3. **Change impact** — What does the 24h dedup TTL bound, what breaks at 60s?
   - Answer: bounds how long a GitHub redelivery is still recognized as a duplicate; matches GitHub's own ~24h redelivery window. At 60s, any redelivery arriving later than that (common after an outage/backoff) would find the key expired and enqueue a silent duplicate review. User confirmed ("yes").
- verdict: APPROVE stands. Q+A logged, milestone cleared to mark done.
