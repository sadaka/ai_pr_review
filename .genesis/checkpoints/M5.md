## Micro-plan · 2026-09-06

**User design decisions (2026-09-06):**
1. `overall_confidence` = **mean** of surviving (post-dedup) findings' confidence; **1.0 when there are no findings**. Auto-post iff `overall_confidence >= 0.75` AND no CRITICAL finding.
2. GitHub **installation id fetched via `GET /repos/{owner}/{repo}/installation`** with the App JWT, cached per-repo (stays in the M5 boundary).
3. **Post raw** finding text for M5; write the threat-model note describing the markdown/@-mention/`#ref` injection exposure; defer sanitization to the M8+ injection-guard milestone.

**Files (freeze boundary: `orchestrator/nodes.py`, `hitl/**`, `integrations/**`):**
- `integrations/github_client.py` — `GitHubClient`: App JWT (RS256, 10-min, `iat`−60s) from `GITHUB_APP_ID` + PEM at `GITHUB_PRIVATE_KEY_PATH`; per-repo installation-id cache; installation-token cache (refresh at 55 min); `post_review(repo, pr, body, event) -> int` (`POST /repos/{owner}/{repo}/pulls/{n}/reviews`). `httpx.AsyncClient` with explicit timeout + local `_with_retry` (exp backoff) + local `CircuitBreaker` — same self-contained pattern `job_queue/queue.py` uses (no sideways import).
- `integrations/truth_store.py` — `TruthStore` (asyncpg pool, injected): `upsert_review(repo, pr, delivery_id) -> review_id` (idempotent on the `github_delivery_id` UNIQUE index; returns existing row if present, incl. its `github_review_id`), `insert_findings(review_id, findings)`, `mark_posted(review_id, github_review_id)`, `set_status(review_id, status)`. Maps `Finding.title→summary`, `Finding.line→line_start` (`line_end=line`), `suggestion=NULL`.
- `hitl/queue.py` — `HitlQueue` (same pool, injected): `enqueue(review_id, reason) -> hitl_id` → INSERT `hitl_reviews(review_id, reason, status='pending')`.
- `orchestrator/nodes.py` — pure logic + the orchestrating `aggregate()`:
  - `dedup_findings(findings) -> list[Finding]` — group by `(file, line)`, keep highest confidence, append `"\n\n_Also flagged by: <agents>._"` to the kept finding's rationale when >1 agent agreed.
  - `overall_confidence(findings) -> float` — `mean(f.confidence)`, or `1.0` if empty.
  - `Decision` enum: `AUTO_POST` / `QUEUED` / `ESCALATED`. `decide(findings, score, threshold=0.75)`: any CRITICAL → ESCALATED; elif score < threshold → QUEUED; else AUTO_POST.
  - `aggregate(*, repo_full_name, pr_number, delivery_id, findings_by_agent, github, truth_store, hitl, threshold=0.75) -> AggregateResult`: dedup → score → `truth_store.upsert_review` (early-return if already posted) → `insert_findings` → branch: AUTO_POST posts (`event="APPROVE"` when zero findings, else `"COMMENT"`) + `mark_posted`; QUEUED / ESCALATED → `hitl.enqueue(reason=...)` + `set_status`. Returns `AggregateResult(review_id, overall_confidence, decision, github_review_id, hitl_review_id, deduped_findings)`.
  - `_render_review_body(findings) -> str` — markdown grouped by severity; `- **[SEV] title** — `file:line` · conf 0.xx · <agent>` then a quoted rationale. Empty → "✅ No issues found by the automated review."
- `backend/tests/test_aggregator_hitl_e2e.py` — live Tiger DB (skipif no `TIGER_DATABASE_URL`), fake `GitHubClient` recording `post_review` calls. Focused tests + one combined `test_high_confidence_auto_posts_and_low_confidence_queues_and_critical_always_escalates` (matches the demo `-k` verbatim, same pattern M2 used). Each test uses a unique `delivery_id` and cleans up its `pr_review_records` / `finding_records` / `hitl_reviews` rows.

**Threat-model note (satisfies the DONE.html security gate):** the diff under review is untrusted; specialist findings are LLM text derived from it; `_render_review_body` interpolates `title`/`rationale` raw into a GitHub review body. Exposure: a crafted diff could make a finding contain `@org/team` mass-mentions, `#123` cross-links, or markdown that restyles the review. Not a code-execution path (GitHub renders as markdown, no HTML/script). Accepted for M5; sanitization (escape control chars, neutralize mentions/refs, length cap) is deferred to the M8+ threat-model / injection-guard milestone and tracked in the Next list.

**Out of M5 scope (carried forward):** rewiring `orchestrator/graph.py` to call `nodes.aggregate` and to replace the stub specialist nodes with the real M4 agents; the ARQ `run_review` worker that ties webhook → engine → aggregate. M5 delivers and proves the aggregate→gate→(post|queue) unit in isolation, matching the PLAN freeze boundary and demo command.

## Q+A block · 2026-09-07

**Q1 (design decision):** Why does `aggregate()` take `github`/`truth_store`/`hitl` as
injected params typed against local Protocols instead of importing the concrete classes?
- Human: "opted for [Protocol] classes rather than importing concrete classes to make
  the system flexible and decoupled."
- Verdict: CORRECT. Also preserves `dependency_direction` — `nodes.py` imports neither
  `integrations/` nor `hitl/` — and lets the e2e fakes satisfy typing.

**Q2 (edge case):** Redelivery with an already-aggregated + auto-posted `delivery_id` —
what does `aggregate()` do?
- Human: "in the second call with delivery_id nothing will be updated."
- Verdict: CORRECT. `upsert_review` hits the `github_delivery_id` UNIQUE conflict, sees
  `status != 'pending'`, early-returns: no findings inserted, no GitHub post, returns
  `AggregateResult` carrying the stored `github_review_id`.

**Q3 (change impact):** `Finding` → `finding_records` mapping — `title`, `line`,
`suggestion`, and the lossy part?
- Human (after explanation): "specialist agent emits findings whose structure is a
  little different than our table. title goes in the summary column, line no. goes in
  line_start and line_end with the same value. It also loses data if findings lie in
  multiple lines."
- Verdict: CORRECT (`title`→`summary`, `line`→`line_start`=`line_end`, plus the
  multi-line-span loss; `suggestion`→NULL not named but the mapping understanding is
  sound).
