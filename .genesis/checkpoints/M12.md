  - live-credential tests (`test_specialists_e2e`, `test_evaluation::…e2e`, `test_pipeline_e2e::…live`, `test_observability_budget_e2e`, `test_reliability…::…regression`, `test_reviews_api`) already `skipif` on `TIGER_DATABASE_URL` / `OPENAI_API_KEY` — so `pytest -q` in CI-without-secrets just skips them and stays green.
- **decisions that bind us:**
  - `structured_output_only` / `dependency_direction` — a `PromptRegistry` is a leaf like `prompts/loader.py` (reads files, no project imports); specialists already import `prompts`, so `agents → prompts` is unchanged.
  - the prompt **version stamp** should reach the `agent_events` spine (M6) so a review is traceable to its prompt revision — that's a `payload` field on the `span.start` / `llm.call` event, no schema change (partial phase-15 governance value for free).
  - `single_data_spine` — CI + Docker are infra, not data; nothing new persists.
  - the wheel-packages bug: fixing `pyproject.toml` to list all runtime packages is in-scope (it's part of "can this be packaged & shipped").
- **credentials:** none new. CI runs without secrets (live tests skip, eval gate soft-passes). A maintainer *may* add `TIGER_DATABASE_URL` / `OPENAI_API_KEY` as GitHub Actions secrets to turn the eval gate hard — documented, not required.
- **scope tension / design questions (surface to user):**
  1. **M12 = phase 18 (CI + prompt versioning + eval gate) + packaging (Dockerfile / compose / README)?** Recommend **yes** — it closes the last DoD gate *and* directly answers the user's "how do I deploy & run this" (the README + compose file *are* the answer). Trace-viewer / governance-residency / drift → separate later milestones.
  2. **Prompt versioning depth.** Recommend a **content-hash registry**: `PromptRegistry.get(name) -> VersionedPrompt(text, version)` where `version = sha256(text)[:12]`, plus a `prompts/REGISTRY.md` changelog table (name → current hash → date → note) that a test keeps in sync. Specialists switch from `load_prompt("x")` to `REGISTRY.get("x")`; the version is stamped into the agent's `agent_events` payload. No DB table, no migration — the git history *is* the version history; the hash makes it explicit and traceable.
  3. **Docker: one image, N entrypoints, or per-service images?** Recommend **one image** (`backend/Dockerfile`, `uv`-based) with the process chosen by the compose `command:` — `uvicorn webhook_receiver.app:build_default_app --factory`, `uvicorn api.app:build_default_app --factory`, `arq job_queue.arq_worker.WorkerSettings`. `docker-compose.yml`: `redis` + `webhook` + `api` + `worker` (+ `frontend` optional); **Tiger Cloud stays external** (a `TIGER_DATABASE_URL` env var — the migration is a documented one-time `psql -f`). Matches §4.3's "greenfield, not zero-downtime" posture.
  4. **CI: one workflow or two?** Recommend **two** — `ci.yml` (mypy + pytest on every push/PR, no secrets) and `eval-gate.yml` (the M9 `regression_gate` on PRs touching `backend/agents/**` or `backend/prompts/**`; soft without secrets). Keep the known 3 `test_orchestrator.py` mypy errors from failing CI via a scoped `mypy` target or an allow-list — recommend fixing those 3 (they're trivial tuple-typing errors in a test) so `mypy .` is genuinely clean and the DoD gate is honestly met.
- **verdict:** **UNBUILT** → await design answers, then micro-plan + L1 BUILD.

## G0 design answers · 2026-09-08
All four recommendations accepted by the user:
1. M12 = phase 18 + packaging (Dockerfile / compose / README).
2. Content-hash prompt registry (`sha256(text)[:12]`), `prompts/REGISTRY.md` changelog, version stamped into `agent_events`.
3. One backend image; compose `command:` picks the process. Tiger Cloud external.
4. Two workflows (`ci.yml` + `eval-gate.yml`); fix the 3 `test_orchestrator.py` mypy errors.
