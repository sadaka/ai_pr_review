Decisions that constrain new work

  • ADR-003 — one Tiger Cloud Postgres-compatible spine for memory/truth/time, not three separate databases; Redis stays queue/cache-only → see ai-pr-review-agent.html §2.2–2.4
  • M1-fix-1 — migration must explicitly CREATE EXTENSION timescaledb_toolkit (not just timescaledb/vector/vectorscale) because the continuous aggregates use percentile_agg/approx_percentile, which are toolkit functions — do not remove this line even though Tiger Cloud pre-bundles the extension
  • M2-dedup-ordering — the webhook handler claims the Redis dedup key (mark_seen) before enqueueing, not after: this is what prevents a crash between "enqueue" and "mark-seen" from letting a GitHub redelivery double-enqueue the same job. The tradeoff is a failed enqueue after a successful claim must roll the claim back (unclaim) or a legitimate redelivery gets silently swallowed until the 24h TTL — do not remove the rollback when touching this path.
  • M2-redis-timeouts — job_queue/queue.py builds ArqRedis directly instead of using arq.connections.create_pool, because create_pool only wires a connect timeout, not a per-command socket_timeout. Don't switch back to create_pool without re-adding an explicit command timeout.
  • M3-no-langgraph-checkpoint-redis — deliberately did NOT use the official langgraph-checkpoint-redis package; it requires a RediSearch module (via redisvl) that Upstash's free tier doesn't provide. orchestrator/redis_checkpointer.py is a hand-written minimal async saver against plain Redis instead — narrower scope (no blob/version-delta storage, no cross-thread listing), sufficient for crash-resume, not a general-purpose replacement.
  • M3-resume-input-is-None — LangGraphEngine.run MUST pass None (not {} or any other value) as the graph input when resuming an existing thread — LangGraph treats ANY non-None input as a fresh invocation and re-dispatches from START, re-running every node including ones that already completed. This was M3's actual L4-caught bug; do not regress it.
  • M4-llm-provider-openai — the specialists and the embedding retriever run on OpenAI (openai SDK, chat.completions.parse + embeddings.create(dimensions=256)), decided 2026-09-06. anthropic + voyageai remain in pyproject.toml but are unused / reserved — do not wire them or remove them without an explicit decision. If a provider switch is ever made: llm_client.py + base_agent.py move to the Anthropic SDK, and context_retriever.py embeddings move to Voyage (Anthropic has no embeddings API) — ~4 source + 2 test files, plus a full re-embed of code_chunks (embedding spaces are not interchangeable).
  • M4-agent-type-stamped-in-code — agent_type is NOT part of FindingDraft (what the LLM emits); it is stamped by Finding.from_draft(draft, agent_type=self.agent_type) from the agent's class attribute. Keeps an un-forgeable field (used for M5 aggregator dedup + HITL routing) out of reach of a prompt-injected diff. Do not "simplify" by asking the model for it.
  • M4-specialist-failure-is-empty-list — when the structured LLM call returns parsed is None (refusal / unparseable / length cut), SpecialistAgent.review() returns [], never raises — one specialist must not break the M3 parallel fan-out/join. Consequence: a persistently-failing agent is currently indistinguishable from a clean one until M6 emits llm.call outcomes to agent_events.
